# 订单工作区重新开始

本操作用于运营明确要求清空既有订单、导入及其关联业务记录后，重新导入原始报告。普通归档和个人资料匿名化不能替代本操作：归档仍保留订单身份，已匿名化的同号订单会拒绝重新导入。

这是独立、可恢复的离线维护。遵循 ADR-002 的迁移及备份边界；应用和导入始终使用 `withTenant()` 与非 owner 角色。维护工具不提供常驻删除 API，也不改变正常运行中的不可变历史保护。

1. 记录运营授权、当前成员身份及权限、实际运行提交、数据库、对象和队列清单。读取完整备份并验证恢复；正式采用前冻结写入，备份和过滤计划必须绑定同一个快照。
2. 在隔离恢复库以当前成员的 RLS 上下文投影旧订单、报告批次、主键和完整复合外键。`tools/scripts/order-reset-plan.mjs` 仅计算精确行集合，不连接数据库或执行删除。旧 `order_source_snapshots` 也须清理，否则原来源身份会阻止重新导入。
3. 保留店铺、商品、规格、销售及制造版本、规则、供应商、基础编辑项目和审计主表。命中基础资料、实物流水、库存预留、付款或产能占用时中止，先核对真实影响。不得按表名、租户整表或对象前缀推测删除。
4. 在离线库检查其他租户的精确类型业务软引用。创建新候选数据库，按 `pre-data → 保留数据 → post-data` 恢复完整结构、权限、RLS、函数、触发器及约束。不得关闭触发器、设置复制绕过模式或放宽线上 RLS。
5. 比较每张表的预期保留行数及逐行摘要，验证全部其他租户和基础资料原值。核对迁移链、函数、触发器、约束、ACL、RLS，以及应用非 owner 的真实读取结果。旧订单、导入、生产、发货及关联待办须保持一致。
6. 对对象和队列单独处理。对象必须先解析明确归属，排除所有保留引用，再按完整 key 及版本核对；无法枚举的对象须明确记录，不能声称已全部清除。任务必须匹配本次旧批次、原请求或旧业务 ID，不清空 Redis，也不唤醒无关消费者。
7. 验收通过后在启动锁内切换，保存原库和完整备份作为私有恢复来源，记录失败补偿步骤。恢复日用运行后，再通过真实认证入口导入报告；同号重导不能重复创建订单。记录附件解析的实际结果，保留审单和生产审批门。

私有原始报告、ZIP、对象 key、客户资料、数据库连接和本机操作记录不进入公开仓库。业务重置不等于实际取消工厂生产、撤销外部发货或资金交易；存在此类事实时须先核对对应业务。保留的私有备份不是当前工作区数据，后续按备份及资料保留制度管理。

## 报告附件后台处理

可选报告任务使用已采用的固定源码，队列白名单只包含 `amazon-order-report-processing` 与 `amazon-order-report-retention`，调度器设为 `none`。这仍会消费所选队列中的所有有效任务，因此启用前必须核对旧任务和其他租户。

报告请求人被禁用、失去 `order:write` 或 `order:pii:read`，或其中任一权限范围缩小时，领取、下载及最终采用阶段均停止处理，以 `processing_blocked` 记录原任务。恢复须由当前有权限的人员明确发起；过期资料清理不依赖原请求人的现有权限。队列登记仅表示等待任务服务，不证明后台已运行。
