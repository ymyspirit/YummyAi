# 销售制作确定性出图的持久恢复

2026-10-19 · R09/R20/R39、B16/B28。复用已安装 BullMQ、原 PostgreSQL 任务、Drizzle 与生产处理器；没有新增外部依赖。

## 原始任务与投递

原 `production_editor_renders` 是持久意图；Redis 只保存可丢弃的投递。0127 新增只含租户 UUID 的 `production_render_dispatch_tenants`、任务执行租约、下次派发时间和索引。迁移只从组织路由 ID 补齐历史目录，不在无租户上下文中读取制作或顾客资料；新任务在原事务由 invoker 触发器登记自己的租户。

目录采用非 owner 应用角色和强制 RLS：可以列举基础路由 UUID，只能登记当前租户。项目、任务、选项和文件继续通过 `withTenant()` 读取。目录 UUID 不授予任何业务权限。

恢复覆盖原订单审核正式导出，以及绑定原配方/SKU 的销售制作预览和正式导出。未完成所有者权限核验的独立底稿和订单普通预览不扩大恢复范围。`image_edit`、整单美化及其他付费调用不自动派发；既有付费提交中断保护保留。

销售确定性任务首次入队失败仍保留 queued 和可解释诊断。调度器也识别旧 `queue_unavailable` 失败，但仅在解密后的原选项确认为受支持确定性出图时恢复。新任务先留十秒给原投递；每次派发以数据库原子预约节流一分钟。处理一条失败或无效快照不能阻断其余租户。选项和提示词不进入队列或明文日志。

恢复投递可以有新的传输 UUID，关联始终为原 render ID、租户和原 requestedBy，不新建制作任务、版本或配方。数据库租约和原 processing token 控制实际执行；不能依赖 Redis 已完成 job 的残留来判断业务已完成。

## 执行租约与结果

Worker 在行锁内核对原申请人。已完成记录或仍有效的 processing 租约不重新执行；失效租约才允许接管。新租约为两分钟，执行期间每十五秒按原 token 续期。旧记录没有租约时，以原更新时间加两分钟作为兼容期限。恢复确定性任务不提高原测试超时，也不改写原图案或工艺。

原 token 隔离心跳、失败处理及最终采用。旧执行器失去 token 后不能采用其存储结果，也不能把新执行器标为失败。来源、当前成员/授权、原版本、审核和制造门禁继续由原处理器核验；恢复不提供额外授权，不替代生产发布。

完成或失败清理执行租约。新发布知识或方法、今天的商品值不能补写旧任务的固定输入。原已完成文件的读取和历史引用保持原授权规则。

## 验证与正常升级

使用隔离 `--suite=catalog-scope-integration`；可同时传入 `src/design/production-editor.integration.test.ts` 与 `src/orders/order-workspace.integration.test.ts` 回归旧制作和订单路径。新用例覆盖真实隔离 Redis 投递清空后的原任务恢复、活跃/过期租约、实际心跳、旧执行器 token 隔离、当前权限撤回、旧运输失败、付费排除与 RLS。队列、桶、数据库和合成来源均由测试拥有，不能清空普通 Redis 或普通业务库。

API、Worker 和 database 必须使用同一源码及完整迁移链。0127 仅在可清理隔离库验证；普通数据库仍需独立备份、应用迁移、验证恢复和 CI 后再启用。Worker 的现有迁移哈希检查会拒绝缺失迁移，不在启动时偷偷迁移业务库。实际本地结果与清理状态见[本批交付](../project-control/CATALOG_RENDER_RECOVERY_DELIVERY_20261019.md)。
