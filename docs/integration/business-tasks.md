# 商品与订单业务任务

入口是 `/business-tasks`，默认展示 [工作流待办](workflow-task-inbox.md)，按当前责任范围筛选真实节点并读取完整计数。业务对象选择器保留订单和上架方案；旧 `/ai-tasks?business=1` 链接保留参数并跳转，只有 target 而没有 object 的旧链接继续打开订单。商品上架读取本人现有的上架准备任务；订单读取同租户内有权限访问的整单依据。订单、制图、生产及发货详情也提供「本单任务与执行依据」。读取与刷新均不派发模型、购买面单或提交工厂。

## 业务分工

订单责任待办现由 [逐商品跟进](order-line-responsibility.md) 补充：本人、未分配、全部可见及内部时限/当前异常的受权投影；进入具体商品仍查看下述整单依据。责任安排不代替整单或逐件完成状态，资料到期不算完成，旧订单深链接继续保留。

统一视图展示目标、阶段、固定版本、阻塞、下一步和可用执行记录。上架沿用 `SalesPlanPreparationService` 的检查点、有限分析次数和审核边界；订单协调器复用现有审单、制图、正式导出、生产、物流与工厂交付服务。各业务服务仍拥有状态、权限、幂等与重试。新增协调器没有自由工具执行、模型路由选择、SQL 写入或另一套队列。

订单阶段包括审单依据、制作检查、审核校样、正式文件、工厂排期、物流面单、文件交付、生产质检和实际交运。每个读取来源保留独立失败状态；缺失与部分结果不会算作通过。物流准备完成、交付包准备完成、工厂接受、质检和实际发货分别表示不同事实。

## 接口

| 路由 | 输入和行为 |
| --- | --- |
| `GET /v1/order-centers/lines/:id/task` | 以订单商品为入口读取整单任务。返回 `task` 阶段与指标以及 `groups` 工厂分组、当前交付包、阻塞和依据指纹 |
| `POST /v1/order-centers/lines/:id/task/prepare-delivery` | 严格输入 `{ groupId, expectedFingerprint }`。重新读取业务依据，准备该工厂的正式交付包或返回已有包 |

两条路由均要求 `OrderRead`、`OrderPiiRead` 及 tenant 数据范围；写操作还要求 `OrderWrite`、`DesignRead`、`AssetRead`。模块读取继续执行各自权限与 `withTenant()`，不接受调用方租户选择。Web 代理沿用同源 JSON、路径白名单、请求上限和 private/no-store；拒绝额外查询参数。视图不返回顾客地址、模型原始提示、凭据或存储对象键。

## 交付衔接

1. 核对当前整单资料与正式文件，所有商品完成生产排期后，按供应商、实际工厂及工厂地址版本分组。
2. 每个当前生产版本必须有已完成、可用的物流依据。缺少包装、工厂、交期、可用渠道、预算或面单时，从原物流任务补齐；不从本视图自动购买或重建物流单。
3. 操作者点击「准备该工厂交付包」。服务重新核对订单、制作、生产及物流版本，变化返回冲突；原交付服务再次核对权限、工艺、完整 JPG、审核、质量门禁及物流面单。
4. 相同租户、工厂分组和依据生成稳定请求键，由原交付服务持久化并锁定。并发点击或提交成功但响应丢失后，重读会找到原包；重试不会另建相同包。超出最近列表的原包通过生产记录引用读取。原包必须包含当前物流任务及面单校验值；只含生产图的旧包保留，另建包含当前物流依据的新包。资料改变必须重新读取，不能携带旧指纹提交。
5. 在现有工厂交付页下载、上传 ERP 并登记真实提交、接收、接受或拒收。工厂接受不会自动生成质检或发货证据。

当前快捷交付只覆盖满足现有异形抱枕规范的完整数量。返工、部分数量、其他产品类型、超出 50 项的分组或未完整读取的记录，回到原业务页按对应供应商规范处理。不同工厂分别准备包；无工厂版本、取消、暂停、归档、来源变化、缺面单或读取失败都会阻止准备。现有手工交付入口和其他供应商流程继续保留。

查询最多显示 100 个交付候选及 20 个交付包、100 个物流任务，超出范围明确提示。不可读的制图执行记录影响指标可见性，不替代正式文件服务的实际验证。该视图不建立新的不可变订单快照，历史依据由各原任务和交付包保存。

## 执行效果

上架展示当前通过检查数、建立至最近检查点的时间、已确认业务调用数及最近分析的费用。订单展示各商品最近制图任务的首轮检查通过数、重试次数、有凭证的人工结果恢复、已结束步骤耗时和渠道回报费用。首次通过要求 preflight 首次完成且无错误或待人工判定项，仍不代表运营审核通过。

费用未知保持未知，模型费用与物流报价、实际费用分开，不同币种不汇总。最多展示最近 7 个物流任务费用，完整记录在原物流页。耗时不冒充完整履约周期，人工恢复数不冒充全部人工干预，当前版本任务的指标也不等同长期运营评测。

## 验证

投影单元测试覆盖当前校样版本、取消与来源变化、部分质检、平台确认及未知费用。真实租户数据库集成测试使用隔离物流读取适配器验证分工厂交付、重复与并发请求、指纹变化、权限及租户隔离。物流浏览器验收使用隔离 OMS 服务和真实 API/Worker，验证面单与 JPG 入包、刷新找回原包、失败重读、桌面及 390 px 页面；运输服务同时核对无重复购单。隔离运行器在 finally 中清理数据库、对象桶及 Redis，并保留清理清单。

```powershell
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e:order-daily --suite=all-integration
pnpm test:e2e:order-daily --suite=logistics
pnpm test:e2e:order-daily --suite=sales-launch
pnpm test:e2e:order-daily --suite=ai-tasks
pnpm build
pnpm start:local
pnpm check:local-runtime
```

浏览器测试与构建前停止本工作区的 Next 开发服务；物流验收还需释放其 API 端口。真实物流自动购单仍以原账户权限、发货配置、规则和预算核验为前提。这里的隔离验收不代表真实物流账户或工厂已接收订单。

2026-10-13 本地验证：lint、全工作区类型检查、单元测试、全量集成命令及构建通过；物流与上架浏览器套件共 10 个场景通过，上架套件包含 AI 任务工作台回归。桌面与 390 px 页面已检查，模拟物流记录为 1 次创建、0 次重复、0 次越界请求。5 次隔离运行（包括修正前的一次测试失败）均已核对数据库、存储桶及 Redis 清理成功。最后恢复本地 API/Web 并通过 `check:local-runtime`。该记录是本地工作区验证，不代表已发布或真实物流账户认证。

采购、售后与独立异常也可从业务对象选择器进入，分别以原采购单、售后 case 和异常事件投影当前任务。共享责任、筛选、分页和通知界面，详细开通/权限/到期恢复及仍未覆盖的原异常解决表单见 [三类业务跟进](business-followups.md)。
