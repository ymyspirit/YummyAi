# 内置 Agent 的原订单履约接入

2026-10-22 · PRD1.1.98 · 3f7a21d8 · 本批局部隔离验证及自有清理通过

本批将已验证的 fulfillment-v1 接入独立 erp-agent-native-v3。旧十一类读取与履约三种固定范围在同一持久任务中组合，仍只有十二类 reader；同原单的 production、shipments、logistics 是三个绑定，不是三个任意工具。原 native-v1/v2、历史请求、费用、pin 和来源 ABI 保持。完整48需求/54工作包/8阶段目标不缩小。

## 数据与调用

复用原 OrderReadOwner、原生产/数量/交付/发货读取及 LogisticsReadOwner。生产、质检组、制造依据、工厂来源证明和纯加密 codec 从原 API 机械提取，API 委托共享 owner，Worker 使用同一实际实现；不通过 HTTP 执行有保留清理副作用的读取，不 import API 业务服务，不另存事实。

共享 SharedAgentFulfillmentGateway 保留 fulfillment-v1 的原定义、权限、输入、投影和前后复核。新增历史访问核验只检查固定旧 source IDs、原保留期、私有 key 与当前逐项权限；正常订单修订、工厂绑定解除或新观察不自动抹掉有权历史。原来源失效后不继续返回旧封存私文。

## Harness 与版本

新任务固定十二类读取范围、原模型、预算与三个读取执行 pin。运行器继续复用 NativeRuntimeEngine 的原租约、账本、响应检查点和原请求恢复，通过独立协议提供严格输入/输出、分页语义与来源核验。旧协议适配器和 DTO 不接受新增工具。

履约每页最多10条，游标由运行器管理。观察同时记录 indexComplete 与 collectionComplete；履约 collectionComplete 为 null，原每页 coverage.complete 永远 false。读完索引不能当作业务资料完整。模型只选择定义、固定绑定读取和完成方案；正式操作仍先逐项准备，再由原业务核对和明确确认。

每次新模型提交前核对已读对象及原私有来源，再完整重读已封存的履约页。finish 和 prepare 也按每页原 kind/pageSize/cursor 核对完整 business basis 与 sources，不能只检查第一页索引。索引或订单序号未变、第二页质检/交付/工厂作废依据已改变时，旧建议不能采用。实际复读消耗工具调用上限，已付费响应复用不重买。

为新版本追加177迁移与独立数据库 guard，不改旧175/176函数定义或历史列。原176的3384源、389依赖链接及23文件图像运行库已固定供真实升级验证；旧版本由原版本 router 继续恢复。普通148保持，不用当前新源直接启动。

## 界面与验收

本人工作台复用公共任务框架，v2/v3使用各自严格 client、意图命名空间、回执与 prepare 端点，不转换旧请求。履约绑定复用真实原订单候选和事件修订，证据复用原履约组件，知识、无限画布、批量和无人设计保留。

计划验收包含当前真实 Worker/API 来源对照、十四绑定同任务、来源变化、精确费用/质检/作废语义、分页、当前逐项权限、来源保留失效、付费状态恢复、原准备/确认、真实176升级及本人编译页面。所有运行都通过 disposable runner；静态通过不计为运行或业务验收。新旗标 E2E_AGENT_NATIVE_V3_ISOLATED 与复用的16旗标均须在连接前验证，普通目标必须拒绝。

本批测试、编译候选、旧源副本及其他自有输出在检查后删除，保留源码、结论与清理记录。当前结果、实际范围和续做入口见[专项进度](../project-control/ERP_AGENT_NATIVE_V3_PROGRESS_20261022.md)。实际宿主、普通采用、真实模型质量/账单、CI、恢复演练和完整平台继续。
