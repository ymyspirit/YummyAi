# 发货生产来源与数量追溯

状态：本次来源追溯切片已通过本地技术验证，见[交付记录](../project-control/SHIPMENT_SOURCES_DELIVERY_20261019.md)。关联 R23/R26/R30、B38/B42；完整48需求、54工作包和8阶段保持。普通环境尚未采用，完整工作包和真实业务尚未验收。

## 已确认缺口

现有包裹行只保存订单商品行与数量。审核限制了订单总量，但没有固定实际取用的生产单版本及质检记录；同一商品部分发货后，也不能准确区分已经交运与仍在厂内的生产批次。检验缺陷尚无独立影响数量，部分合格与部分返工不能靠现有整批通过字段推断。

参考 [ERPNext Delivery Note](https://docs.frappe.io/erpnext/delivery-note)、[ERPNext Batch](https://docs.frappe.io/erpnext/batch) 与 [Odoo 19生产库存关联源码](https://github.com/odoo/odoo/blob/19.0/addons/mrp/models/stock_move.py) 的来源关联思路，沿用现有业务模块，不引入另一套ERP或库存事实。

## 本次已实现的边界

1. 每个新包裹商品行明确分配生产单、生产版本、原通过质检及数量。分配总和必须等于该行装箱量；当前整批质检模型仅允许通过的生产批次成为来源。
2. 候选数量由生产数量、当前原版本质检和其他已审核/已交运分配计算。草稿不占数量；审核时在同一订单及生产锁内重新核对并占用，改版在新审核提交时切换占用。
3. 审核和正式出库分别复查来源。来源改版、质检变化、停单或数量被其他包裹占用时保留原请求与草稿并报告冲突。实际物流事实另行保留，不能为回到可发状态而删改已交运记录。
4. 发货版本及其来源分配不可变。相同请求只恢复自己的原回执，变更内容或操作员不得复用同一请求；重试仍检查当前受权。
5. 新来源由操作员核对并确认。单一候选可作为建议展示，多批次必须明确分配；刷新不静默更换原选择或吞掉其他填写。Agent不替实际装箱、检验或交运确认。
6. 旧包裹保持原行、原回执及“来源未记录”状态。不得从商品行或今日可用库存猜补旧批次。旧请求恢复保留；新的不确定来源必须明确阻断并说明核对入口。
7. 当前仅有行级部分发货的历史不能证明某个旧批次尚未使用。对来源不明的历史保留诊断与必要的人工核对，不把它当作可重复使用的批次余额。
8. 所有读写通过当前订单权限和非所有者租户事务，数据库强制RLS；分配的商品、生产版本、质检和包裹归属使用租户复合外键核对。只写发货模块拥有的数据。

## 三层分工

数据层保存不可变的发货版本和生产/质检来源分配，保留历史缺失。Harness层负责当前权限、原版本、并发数量、请求指纹、出库前复查及原响应恢复。Agent层可以提出候选，不能伪造物理批次、合格证据或操作员确认。本次不新增收费模型、普通Worker或外部发货调用。

## 连续建设边界

上述来源分配先把已有整批通过的生产记录贯通到发货。部分合格品的实际分组、不同缺陷的独立影响数量、返工批次的替代与分割、历史来源人工核对，以及售后补寄的独立履约需求仍须继续完成，不能以本次新表代替这些业务事实。它们属于同一完整平台目标，B38/B42在完整验证前保持进行中。

## 验证要求

覆盖错商品、错租户、错生产版本、失败/过期质检、分配总量不符、同批次并发超占、改版切换、已交运来源重复使用、来源变化后出库、原请求恢复和当前失权。旧模式真实升级保持原行及原回执，不补造来源。通过实际Web/BFF/API检查选择、确认、冲突保留及桌面/手机操作。一次性数据库、桶、Redis和本轮临时文件在检查后清理并独立核验；既有548条拒绝路径不重试。


## 平台确认与实物交运的独立边界

平台先确认、实物尚未交运时，允许按在厂实物重新逐项检验。已有平台通过回执的发货单只能在原运单、商品、数量和计划参数保持不变时修订生产来源；该限制在后续草稿版本仍有效，不能先建一版再绕过。新版本重新审核，原平台回执继续固定原版本，不能自动借给新版本。已有实物记录的任意旧版本不再进入修订路径。仅有“已发货”状态、却没有实物或平台依据的旧记录明确阻断，等待人工核对。

平台确认后的运单或数量更正、来源缺失历史的人工对账、售后补寄的独立需求及部分合格实物分组继续由原业务拥有者建设；本批不会以通用编辑器暗中改写平台。
