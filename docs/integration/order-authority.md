# 订单工作台与业务跟进的当前授权

2026-10-19 · PRD 1.1.18 · R01/R19/R36/R39，关联 B06/B07/B25/B26/B28。
复用现有 authz、order-core、followup-core、Drizzle/PostgreSQL，不新增路由、依赖或迁移。

## 授权与订单归属

原订单模型没有可信的个人或团队拥有者绑定，责任分派只记录跟进安排。
订单权限目前需要其自身的 tenant 范围；self/team 不能借其他角色的 tenant 范围访问全租户，
也不能由“分派给我”推导数据授权。可信订单拥有者/团队绑定仍属 B06 后续建设，
本批不把暂时拒绝窄范围操作作为完整对象授权模型的完成。

| 路径 | 必要订单权限 |
| --- | --- |
| 工作台列表、筛选全选、经营订单数量投影 | `order:read` |
| 私有详情、整单兄弟商品、研究复盘输入、保存版本及原文件 | `order:read` 和 `order:pii:read` |
| 保存、归档恢复、平台截止、制作状态动作和订单图片上传 | 前述读取权限及 `order:write` |
| 安排责任与时限 | 前述私有读取权限及 `order:assign` |
| 登记/解决订单异常、重放原命令 | 前述私有读取权限及 `order:write` |

每项所需订单权限分别检查范围。制作动作按原逻辑另需 design:write/review，
并在所属写事务中复核其当前存在性；素材读取也保留 asset:read 门禁。
其他素材、设计、财务及履约模块的完整对象范围仍需独立核验，不能由本批通过替代。

## 统一事务与请求上限

authz 的 `intersectPermissionContexts` 只组合相同用户/租户，逐权限取请求上限和
当前范围的交集，移除被撤销的权限，保留双方共同信任的团队。
原请求未具备的权限不会因角色后来扩大而自动获得；提供范围表但缺少某权限时不回退全局范围。

order-core 的 `withOrderAuthority` 保留原 `withTenant()` 与非 owner RLS，
在实际读写事务中校验请求上限和当前成员，而不是仅依赖控制器。
订单工作台 40 处原事务接入此边界，另有五处预览/文件 I/O 预检及复核。
普通读写事务对当前授权行加共享锁；既有只读 repeatable-read 报告仍保持只读，
不尝试在只读事务中加行锁。显式非成员凭据适配器保留其服务端授予的权限上限。

订单版本、订单时间匹配、原始报告、生产/客户审核、幂等及恢复拥有者均保持。
原保存/动作重放在读取回执前复核所需当前权限；写入完成后读取详情所需的权限也事先检查，
避免先修改再因不能读取返回结果而失败。

## 文件与外部 I/O

私有图片读取在文件 I/O 后通过原工作项重新校验当前订单与私有读取权限。
印花素材读取返回前也重新检查订单权限及 asset:read；固定原文件读取保留原版本复核。
上传在扫描/存储前、原图与预览存储之间、关联素材事务中复核权限。
存储途中撤权时不继续第二次写入，也不创建可读取的订单素材关系。
已经完成的私有对象写入不能被假装撤销；未引用加密对象沿用引用感知清理要求。
不得删除其他不可变版本可能共用的内容地址，也不能召回已返回的文件字节。

## 业务跟进与通知

订单逐商品跟进、采购、售后和订单异常的父级跟进入口、列表/计数、分派、候选人
及派发时接收人均按各自 read/write/assign 权限检查范围，并交集原请求和当前授权。
只读可见不表示可以处理；处理范围不足的成员不能成为实际处理接收人。
通知读取针对本人，notification:read 的 self 范围不被误当成需要租户范围。
原提醒截止、去重、派发租约、部分失败和历史证据保持，不创建新的业务事实表。
