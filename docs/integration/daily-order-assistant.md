## 实施与验收边界

先从当前采用源码建立隔离开发工作树。维护根目录存在大量其他未提交工作，不能用旧 HEAD 或旧迁移尾号替换日用 schema194。新工作树遵守本地制品数量检查；保留当前与回退版本。

导出采用开源 ExcelJS（https://github.com/exceljs/exceljs），迁移工具模板时去除所有示例订单和个人资料，只保留格式及非私人参考表。不以用户电脑上的绝对路径作为服务运行依赖。

契约/算法单元验证覆盖一单多件、混规格、未知尺寸、超限、数值格式与公式注入；隔离接口验证覆盖原订单绑定、跨租户、权限撤销、幂等重试、版本冲突、隐私到期；真实编译页面验证桌面与窄屏操作。既有导出与新导出按业务字段逐单比对。测试资源及本轮临时输出验后清理。

采用前需完成当前候选要求的检查、备份恢复与准确源码配对。后台下载消费者单独核对；不因表格接入启动其他历史任务。技术验收、日用采用、运营验收分别记录。

## 原生入口与接口

订单中心保留统一整单列表；详情中的工厂导单链接进入原物流下单页的「工厂导单与物流表」。物流页新增包裹配置、整单预检、导出历史及面单登记。订单地址、审单、规格和正式生产交付仍从原页面修改。

接口位于 `/v1/logistics/documents`，沿用个人身份、租户成员和订单资料权限：

- GET `options`、`exports`、`exports/:id/file`：配置选项、历史及授权下载。
- POST `profiles`：保存与实际工厂版本、原产品规格版本关联的不可变包裹配置；版本冲突时刷新。
- POST `preview`、`generate`：预检后以相同资料指纹生成，重复提交复用文件；订单事实变化时要求重新预检。
- GET `exports/:id/label-basis`，POST `labels`：核对当前资料后登记云途跟踪号及原始 PDF。
- GET `labels`、`labels/:id/file`，POST `labels/:id/handoff`：读取最新有效面单，按原正式生产包生成义彩文件夹。

工厂草稿可维护包裹配置；导出要求工厂已启用且版本一致。工厂资料更新后重新保存导单配置。生产表必须完整覆盖整单所有商品和数量，原交付包继续验证审核、规则快照、工厂绑定及文件哈希。义彩文件保留已批准 JPG 的字节，不重做生产图。

迁移 0195 增加物流配置版本、导出、订单关联与人工面单表。全部租户表强制 RLS；配置/导出追加版本，导出和面单私有内容在原订单 PII 加密域保存。原订单匿名化及保留期清理同时移除相关密文；旧元数据继续保留审计。PDF 经过实际 ClamAV 扫描，私有文件下载每次重查权限与当前来源。

## 已下载 ZIP 的承接

订单报告页新增批量原始 ZIP 承接，最多一次选择 500 个、单文件 20 MiB。按 `订单号_订单项号.zip` 提议匹配当前店铺和批次；SKU 不参与身份匹配。服务端仍经原上传接口扫描、解析并核对 ZIP 内的订单/订单项及站点、卖家信息。文件名不是可信身份凭据。

已有 ready/partial 内容、已复核、处理中或过期的条目跳过；中断后可重新选择。逐文件读取当前版本再上传，防止覆盖同时发生的更新。离页会中止当前客户端请求；下一次读取服务端事实决定是否继续，不自动标记复核或生产完成。

`tools/scripts/prepare-order-assistant-migration.py` 只读预览旧助手资料；提供 `--output` 才创建新的业务迁入目录，拒绝覆盖和源内容变化。它按 ZIP 的 marketplaceId 拆分混合站点报表，保留每个单元格值及原报表/ZIP 哈希。实际导入仍在个人登录的原订单报告入口进行；不会把本地状态写入 ERP 数据表。

```powershell
python tools/scripts/prepare-order-assistant-migration.py --assistant <旧助手目录> --report <原始报告> --store <店铺名> --output <新的业务目录>
```

迁入目录含买家原始资料，放在业务文件目录，禁止入 Git、测试日志或公共制品。较早批次独有项、手工包裹调整和地址修正单独列入预览，不推定取消、已发货或已获生产批准。
