# 定制订单承接与异常修正

入口：**订单与履约 → 订单中心 → 打开订单商品 → 制作需求 → 定制订单承接核对**。

第五批复用订单导入、渠道 SKU 映射、加密需求版本和原制图/审核流程。首轮受控验收为
Amazon 美国站、Custom FBM 异形抱枕，两个尺寸 SKU。没有新增表、迁移、环境变量或
模型调用。核对通过只表示字段、资料归属与固定版本满足承接条件，不证明模型图像质量、
平台配置生效、生产稿合格或工厂接受。

## 承接与处理

1. 通过原商品开发渠道映射登记店铺、站点、平台 SKU、刊登标识、资料包及真实生效时间。
   导入订单按下单时间选择唯一的映射，不按今天最新的销售方案覆盖历史。
2. 打开订单，核对原始资料与制作依据。新受控资料包读取封存的定制字段、区域、
   SKU/规格映射和具名交付核对；与实际印花/制作版本不一致时拦截。
   没有固定印花主文件的来图/文字定制方案可以引用已审核视觉图稿和规格绑定的
   已审核通用底稿；视觉图稿不充当生产模板或本单生产文件。固定印花仍需要原
   已审核制作模板。后续私有制图、生产稿检查和运营审批不因此跳过。
3. 点击“核对当前需求”，可以检查尚未保存的修改。缺少原图、字段歧义、重复值、
   字段类型不符、无效选项、文字长度或版本冲突会显示具体待办。图片预览字段不代替
   买家原图，图片内容不能作为文字字段接受。检查不会推送制作或调用模型。
4. 页面自动整理常见选项、同组文案与字体颜色，唯一字段匹配直接用于确认时的规范化草稿。
   额外原始选项保留供无人设计与运营核对，无需逐行指定模板字段；不确定项可显式使用
   “AI 分析并填写”，仅采用有本次原始证据的绑定。需要重新匹配时使用“使用下单时渠道映射”。
   原始分组、未保存草稿绑定和模型预算边界见[订单需求解释](order-requirements.md)。
5. 资料不足可保存为待补资料。补图、改字或重新核对导入资料后，保存为新的需求版本。
   已派单先按原流程撤回；已经生产或存在有效生产单时仍受原变更门禁约束。
6. 确认审单与派单时服务端重新验证。清晰度、主体尺寸、单双面、裁线、条码框、
   Rule Center 快照、模板、运营审核与生产放行继续使用原固定版本和原门禁。

有受控渠道资料的订单不能通过移除资料包引用绕过检查；也不能把另一个店铺/商品的
资料包或原图套入当前订单。历史资料包缺少第四批快照时明确显示缺失，继续按原固定
印花/工艺人工核对，不补写今天的规则或配置。

已保存订单的资料包引用保留在不可变的加密需求版本中。销售方案修订或后续渠道映射
不会自动替换该引用；历史匹配仍需属于本订单的店铺、站点、平台 SKU 和下单时间。
人工改选资料包必须通过对应匹配检查，并保存新的需求版本。模型、规则和工艺不被
承接核对重新批准或放宽。

## 接口、安全与恢复

`POST /v1/order-centers/lines/:id/intake-check` 接收 `expectedRevision`、
`expectedSourceVersionId` 和现有 `OrderWorkDraft`，返回结构化待办、字段状态、
固定包/核对版本和唯一字段匹配建议。要求 `OrderRead` 与 `OrderPiiRead`；租户来自
认证成员，所有读取通过 `withTenant()` 与非 owner 应用角色。响应为 private/no-store。
Web BFF 限定路由和同源 JSON 请求，不接收调用方选定的租户、存储路径或审批状态。

保存/派单沿用原幂等编号与加密操作事件。同一编号、相同内容的已接受请求先读取原记录，
再返回当前订单；响应丢失或后来状态变化不会重复生成需求版本/派单记录。
相同编号更改内容会拒绝。原图、原始报告、需求历史与生产记录保持不可变；失败后
使用原制图流程的有效检查点恢复，不因承接核对重新收费或生成图案。

## 隔离验收

### 2026-10-26 原图与审单一致性修复

已下载图片不等于已绑定定制字段。勾选图片时，若当前印花只有一个图片字段，直接使用
该字段编码；多个图片字段必须明确选择。界面显示「已绑定」，旧的未知用途保留可见，
不能将平台预览或其他订单图片作为顾客原图。

只有已验证的异形抱枕来图印花启用平台选项白名单：Pillow Shape、Style 和
Order Notes for Seller 对应裁切、印刷面数和顾客备注。旧「正面」仅在唯一买家原图
字段的无冲突场景归一；单双面选项写入真实枚举值。原始报告不改写，未映射内容、字体、
颜色、特殊备注不删除，也不会自动将 Agent 改成人工。

直接匹配的 `CUSTOM-SHAPED-PILLOW` 订单中，唯一明确的尺寸选项须与固定规格完全一致，
才作为制作控制参数单独传递；原尺寸字段仍保存于需求及原始报告。多值、错尺寸、附带
字体颜色或与真实定制字段冲突时不隐藏该字段，必须核对。已有封存配置继续使用其原映射。
人工裁切短文本按固定字段的原长度规则保留，自动制图另检查是否支持该裁切。

「核对当前需求」、确认审单和制图计划使用相同归一化结果。预检同时执行所选制图方式
的保存门禁；自动制图不支持的要求返回 `automatic_artwork_not_ready` 和处理动作。
保存待补资料仍可保留这些要求，操作者明确选择人工后可按人工审单。核对通过仅表示
当前输入可确认审单，不表示已经派单、调用模型或批准生产。

新增回归通过个人 OIDC 和隔离数据库，验证默认 Agent 的简单来图审单，以及特殊要求的
阻断、保留和明确人工选择。它们进入默认 daily CI；定向运行：

```powershell
pnpm test:e2e:order-daily --suite=order-daily order-intake.spec.ts --grep="controlled order intake pillow" --workers=1 --retries=0
```

新用例输出位于运行器本次独立输出目录，验收后保留简明结论并清理临时图和日志。
旧 `--suite=order-intake` 是 local-service 历史路径，不可用其结果证明本人 OIDC 或默认
Agent 审单通过。

```powershell
pnpm test:e2e:order-daily --suite=order-intake-integration
pnpm test:e2e:order-daily --suite=order-intake
```

运行浏览器测试和 build 前停止同工作区 Next dev；结束后使用 `pnpm start:local` 和
`pnpm check:local-runtime` 恢复。相关核心检查仍包括 lint、typecheck、unit 和 build。

浏览器使用真实身份、API、RLS、私有存储、订单导入、需求保存与幂等派单；上游制作稿
和成品图片由明确标记的隔离合成夹具提供。人工队列测试不会开始制作，不运行付费模型、
发布商品、联系买家/工厂或下达生产。覆盖两个尺寸、历史包、重复导入、原图归属、
缺图/字段冲突、移除引用、错误资料包、修正、响应丢失和历史版本保留。

精确夹具 ID 与桌面/390 px 截图放在忽略目录 `tmp/order-intake-e2e`。运行器 finally
删除测试数据库、桶和 Redis，并验证不存在；结果见 `tmp/order-daily-e2e-<token>.json`。
该验收不等于真实授权样本的图像质量或实际生产品质验收。
