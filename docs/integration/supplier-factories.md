# 供应商、工厂与产品能力

入口为 **供应商档案 → 供应商详情 → 所属与合作工厂**。一份供应商档案可有多个
实际生产地点；每个工厂独立维护地址、联系人和多个产品／工序能力。

## 资料归属与操作顺序

1. 在供应商资料中确认所属主体性质、企业全称、简称、业务角色、商务联系人、
   办公地址、结算和开票信息。`kind=manual/printify/printful` 是接入方式；主体性质
   `external_supplier/internal_entity/unconfirmed` 单独记录。
2. 在该供应商详情新增工厂，填写自有／合作性质、合作关系、生产地址、生产联系人、
   提货及退货地址、时区、工作时间、截单时间和发货能力。自有工厂归属内部经营主体；
   外部供应商的加工地点在本系统中属于合作工厂。
3. 从工厂名称或「管理能力」进入工厂详情，为不同产品或 SKU 配置产品类型、承接
   工序、整件／部分工序范围、材料、尺寸上下限、印刷面数、工艺标准和模板版本。
   每条能力分别维护核验依据、样品状态、报价、MOQ、交期、日产能参考、有效期、
   返工与运费责任及凭证／文档引用。
4. 生产人员在已审核正式文件的「下达生产」中选择具体工厂及产品能力。服务器
   校验主体与工厂状态、核验状态、产品／SKU、数量、尺寸、面数、工艺标准、限定
   模板和有效期。只有部分工序的能力不用于整件生产。

供应商只需填写名称即可保存；所在地区、办公地址、联系人及商务资料均可后补，
地址或联系人只填写一部分也可保存，未填写的国家不会自动填成 CN。工厂和能力
只需填写名称即可先保存草稿，编码自动生成。未知时区与最低接单量保持 `null`，
表单不会默认填入上海时区或最低接单量 1。
草稿可记录不完整的生产地址、联系人和待确认工序，不能因此获得生产放行。

启用工厂要求实际时区、生产地址的国家、城市、详细地址，以及至少一名填写了姓名和联系方式的生产联系人，且
所属主体已启用、已确认生产加工角色和性质。启用能力须确认最低接单量和实际核验依据，失败
样品不能启用；抱枕整件能力还要确认印刷、裁切、缝制、填充、面数和工艺标准。
核验由操作员根据真实凭证填写，系统不代替工厂确认或最终生产放行。

已审核制作文件带有产品类型时，本单须有有效的物理尺寸。工厂承接范围须同时有
明确的毫米下限与上限，缺少任一边界不会视为无限制；固定单一尺寸可填写相同的
上下限。限定模板和工艺标准仍须分别满足，不能替代尺寸范围确认。尺寸来自本单
固定的实际制作规格，不从商品名称、变体文字或自由文本推断。

工厂候选与实际下达均使用数据库事务时钟判断生效和到期，返工预览沿用同一检查。
下达时重新核对当前工厂／能力版本与全部阻断原因。已固定生产单的原能力快照与
交付历史继续保留，新增规则不回写它们；重新安排和新返工属于新的生产选择。

报价、交期和产能用于制造配置与选择。未知报价／交期／产能保持 `null`。
日产能暂不自动预留，报价暂不自动计费、生成应付或付款。现有「供应产品」
继续负责供货报价和采购来源，见 [product-suppliers.md](product-suppliers.md)。
文档引用是人工维护的编号或链接；本模块不上传附件、自动取回文档或联系工厂。

## 数据与不可变版本

迁移 `0094_supplier_factories.sql` 新增：

- `fulfillment_suppliers.profile`：业务主体资料；旧记录默认性质待确认、角色与地址
  留空，不把原地区自动当作实际工厂地址。
- `fulfillment_factories` 和 `fulfillment_factory_versions`：固定供应商归属、工厂编码
  与当前版本投影，以及不可变的资料版本。
- `factory_capabilities` 和 `factory_capability_versions`：工厂的产品／工艺能力投影
  与不可变版本，可限定产品、SKU 和接受的工艺模板版本。
- 生产单固定 `factoryId`，生产版本同时固定工厂资料和能力版本；交付包 V2 固定
  具体工厂及资料版本，清单条目保存该生产单的完整能力快照。生产批次与交付包
  不能混用不同工厂，交付包还要求工厂资料版本相同。

资料或报价修改追加版本，已有生产单和交付包保留原版本。地址修改不会自动重定向
已经下达的生产单。暂停工厂／能力或停用所属主体会阻止后续交付和接单，恢复启用
也不会改写旧清单。调整生产地点须经生产人员核对后重新安排。

旧生产单和 V1 交付包保持原有记录、文件索引与清单校验值；缺少工厂归属明确显示
待确认。它们不能据此获得新的工厂绑定、交付下载或生产进度授权。需要继续下达
时，人工核对原单进度，使用原有取消／重新安排流程建立确认工厂的新生产单；
已经交付的历史事实保留，不作自动补填。

四张新表均强制 RLS，采用租户复合外键，所有业务查询和写入使用 `withTenant()`
及非 owner 角色。资料和能力版本不授予应用角色 UPDATE／DELETE，数据库触发器
也保护历史。修改使用 `expectedVersion`；幂等键绑定规范化请求，原内容重试返回
原保存版本，改内容重试或并发旧版本保存返回冲突。

## 认证接口

所有接口使用认证会员的租户，要求租户级数据范围；不接受 caller tenant ID。
读操作要求 `order:read`，写操作要求 `order:write`。读响应 `private, no-store`。

| 方法与路径 | 输入与行为 |
| --- | --- |
| `GET /v1/sourcing/factories` | 可选 `supplier` UUIDv7；当前资料、能力及产品／模板选项 |
| `POST /v1/sourcing/factories` | `supplierId`、固定 `code`、`profile`、UUID 幂等键 |
| `POST /v1/sourcing/factories/:id/revisions` | `expectedVersion`、`profile`、UUID 幂等键；不允许更换归属 |
| `GET /v1/sourcing/factories/:id/history` | 工厂资料与产品能力的不可变历史 |
| `POST /v1/sourcing/factories/:id/capabilities` | `profile`、UUID 幂等键 |
| `POST /v1/sourcing/factory-capabilities/:id/revisions` | `expectedVersion`、`profile`、UUID 幂等键 |
| `GET /v1/order-centers/lines/:id/factories?renderId=<id>` | 读取该单审核稿的可选工厂与具体阻断原因；额外要求 `order:pii:read` |

供应商原有创建／更新接口新增 `profile`。下达生产新增必填 `factoryId`、
`factoryVersionId`、`capabilityVersionId`；生产交付新增必填 `factoryId` 和同名
查询过滤项。浏览器工厂配置使用认证 server actions，订单选择使用原有同源代理。
没有新增环境变量、模型调用、外部提交或工厂通知。

## 验证与测试清理

```powershell
pnpm test:e2e:order-daily --suite=factory-directory-integration
pnpm test:e2e:order-daily --suite=factory-directory
pnpm test:e2e:order-daily --suite=production-delivery
```

集成选择覆盖多工厂、版本及幂等冲突、租户与权限、生产及供应商绩效回归、不同
工厂隔离、旧清单兼容及暂停恢复。工厂浏览器选择通过真实页面创建主体、工厂和
能力，查看历史，验证未保存表单、桌面与 390 px 布局；浏览器使用隔离的个人
PKCE 身份，不依赖普通 API/Web 或开发服务身份。相关生产、整单和绩效服务在
集成选择中单独回归。抱枕交付与返工选择使用另一套独立环境验证原有人工模板流程的兼容性；
该环境尚未启用印花 SKU 库。它不证明已启用商品库时可以跳过销售 SKU 绑定。
测试中的核验依据和图像都是隔离环境的合成数据，不代表真实工厂或图案获得批准。

执行前停止同工作树的 Next.js 开发服务。临时数据库、私有桶与 Redis 由 runner
在 `finally` 清理并验证，结果记录在 `tmp/order-daily-e2e-<token>.json`。本地文件
使用本轮独立输出路径；检查截图和 trace 后按交付约定删除，只保留结论、校验与
清理记录，实际拒绝的路径单列且不重试。详情见
[order-daily-acceptance.md](../operations/order-daily-acceptance.md)。
