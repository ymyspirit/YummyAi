# 销售组合兼容身份与归档来源

本模块复用现有 ProductDevelopmentService、SalesRecipeService、SalesPackageService、PostgreSQL/Drizzle 及 React 工作台。没有新增外部依赖或迁移；原非 owner 应用角色、RLS、目录事务锁和不可变配方继续生效。

## 组合身份

`artworkVersionId` 的旧式单印花请求与只含默认绑定的 `printBindings` 是同一组合：primary、正面 whole、0/0/100/100 区域、无字段重映射。传输写法不成为新款式身份，不允许以另一个 SKU 编号重复创建同印花/规格组合。跨渠道别名由渠道映射维护。

原多面/区域/映射/绑定顺序仍属于组合身份；版本 pin 不属于身份。升级相同印花与规格的版本创建新配方；换身份创建新 SKU。绑定顺序没有排序归一化，以保留原制作顺序。

新默认组合使用原 legacy 身份。查询同时识别旧代码生成的默认单印花哈希款式；任一兼容款式已经绑定该规格时，阻止新增重复 SKU。存在旧重复时不删除、不合并、不重写原款式、SKU、Listing、配方或订单。两类旧款式共存时，新规格稳定选择 legacy 款式；只有旧哈希款式时复用该款式。其他业务场景中的旧重复身份仍需明确核对。

款式表对应用保持只读/新增权限，不为行锁扩大为 UPDATE；沿用原租户目录锁和数据库唯一约束串行新组合。

## 生命周期与原回执

新组合、新配方版本、制作启动/确认/审核、渠道 Listing 草稿和新封存命令，在原业务事务内检查产品企划、SPU 与销售 SKU 的归档状态。父来源和可变 SKU 读取采用共享锁，归档与新写入串行；复合创建任一来源不合法时整体回滚。

生命周期检查位于新操作执行路径，不能替代原权限及来源授权。合法幂等回执仍按原请求、操作者和当前对象范围读取，不因归档新建第二份结果。历史配方、包及已保存订单继续固定原引用，不采用今天的版本补造历史。

历史文件导出和真实渠道记录核对沿用各自当前授权及字节校验，归档不被解释为撤销已发生的平台事实。归档不能由新制作命令隐式恢复。

## 界面与契约

`SalesSkuDetail.lifecycle` 独立返回 active 与归档来源类型。新 Web/API/contracts 须共同更新；缺少生命周期投影时停止操作。权限与生命周期分别处理：生产性目录操作按当前状态显示，历史包和受权渠道记录仍可核对。后台刷新取消旧请求，迟到的 active 详情不能恢复已归档对象的制作控件。

组合表单的销售 SKU 输入标签包含 SPU 和规格编号，避免跨商品同名规格混淆。沿用现有白黑蓝、Lucide、表单反馈与 reduced-motion，不新增界面框架。

## 验证与边界

原生 `product-development.integration.test.ts` 使用独立印花复现旧单项/显式默认重复、兼容旧哈希身份和三类归档来源。旧哈希重复为严格一次性数据库中的历史导入夹具，不用于证明生产批准；原版本与回执分别核验。

`pnpm test:e2e:order-daily --suite=sales-composition` 验证实际组合表单、归档后的制作/草稿/封存拒绝、原包 ZIP、晚到详情及桌面/390px，并回归渠道映射和个人商品权限。`--compiled-web` 固定当前 BUILD_ID。上游模型/素材为合成夹具，认证、API、BFF、RLS、原制作审核与存储使用实际本地路径。

完整 B16/B19/B20、旧重复的实际业务处理、正常部署和人工验收继续，软件切片不代替整个平台完成。
