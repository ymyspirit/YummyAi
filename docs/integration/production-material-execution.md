## 依据与拥有者

先参考开源[ERPNext实际耗用](https://docs.frappe.io/erpnext/material_consumption)和[库存出入库](https://docs.frappe.io/erpnext/stock-entry)，复用现有库存流水、预留、重建和原生产制造绑定。固定BOM仅计算有理数计划；操作员确认的实际数量用最多9位十进制文字传输，计数单位保持整件/对/套。1/3的计划不先改成0.333333333再判断超用。

原生产订单拥有者核对当前成员、逐权限的租户范围、原生产修订、制造绑定及行码。物料、单位和供料责任来自原不可变内容和校验值，不能由调用者替换。读取复用交付模块的原制造内容校验，不使用今天目录的BOM覆盖旧生产。历史缺绑定明确显示诊断。

库存拥有者仍独占流水、余额和预留写入；生产物料模块只调用其同一事务辅助方法。锁顺序为当前成员、订单、生产、库存命令/预留、租户共享重建键、维度。重建持原排他键。每次物料记录、库存变动、对应预留事件和审计一起提交；不启动普通Worker或外部调用。

## 操作语义

| 操作 | 实际事实 | 库存影响 |
| --- | --- | --- |
| reserve | 为原BOM行保留指定库位/批次 | 增加预留 不扣实物 |
| consume | 操作员确认的商家供料实际耗用 | 扣实物 使用原预留时同笔减少其余量 |
| release | 释放原生产预留的全部未用余量 | 只减少剩余预留 |
| return | 原耗用记录的实际退料 | 在原库位/批次追加正向流水 不重新打开预留 |
| factory_report | 手工登记工厂自备材料报告及来源编号 | 不扣商家库存 不代表工厂API核实 |
| factory_correction | 更正原工厂报告的数量 | 追加反向事实 不改写原报告 |

退料/报告更正须说明原因，累计不能超过原实际事实。实际耗用或备料累计超过原精确计划须说明偏差。停止或已完工生产不接受新预留；实际补记需要说明原因，不能借补记改变开工、完工、质检、接受或可发数量。

旧“fulfilled”预留事件仍保留原义，不补造扣料。0139只对新增的consumed事件记录负预留变化及原耗用流水；活动余量为原数量加这些变化，关闭后余量为零。重建和页面使用余量，原预留总量不改写。通用库存入口不能直接登记consumption；数据库延迟约束还要求同笔原生产回执。

## HTTP与恢复

读取及写入位于 `/v1/production-orders/:id/materials`，本人回执查询位于其 `/receipts/:key`。Web BFF为 `/api/production-materials/:id` 及相同的回执后缀，验证同源、大小、严格输入、响应业务对象与当前身份。读需要order:read和inventory:read，写另需两项write，均须对应租户范围；写入时重新核对真实成员。

原实际记账只含一笔数据库事务，无需外部执行租约或生产单ID。旧原请求编号回执继续可读；有持久提交的编号只能由原拥有者执行，不能绕过已取消或过期状态调用旧接口。按原编号查询尚无回执时不能断言未执行，原事务可能尚未提交。已成功回执在当前权限下恢复，不因生产状态后来变化而再扣一次库存。

原正文不放入URL或审计日志；自由填写原因加密保存，来源编号及原因仅用于业务说明，不填写密码、买家资料或密钥。工厂报告不是已验真的采购发票，也不自动产生零成本。真实成本、收货检验、物料分类、工厂产能、后续财务以及完整浏览器/部署验收继续原计划。

## 0140 持久原提交

新增 `/commands` GET/POST、`/commands/:commandId` GET，以及其 `/execute`、`/cancel`、`/acknowledge` POST。准备时保存本人、原生产/BOM、规范原正文校验、原权限上限及加密正文，7天到期；每位操作者在同一生产单最多有一笔未确认结果。跨操作者不能借用原编号或读取私有填写。

执行始终采用服务端原文，当前权限与原上限共同约束。在一个外层数据库事务中锁订单、生产及原提交，物料/库存/预留/审计通过保存点执行，成功事实与命令回执同笔提交。可恢复的业务冲突回滚保存点并保存拒绝；审计或运输故障回滚整笔事务，原提交保持待核对。取消等待同一事务，若实际已经保存则返回成功原回执。数据库同时拒绝没有原命令凭据的物料插入、没有成功命令头的独立事实提交及篡改终态。

确认结果只清除原加密填写，保留不可变实际事实、请求校验与原回执。到期清除不依赖操作者重新打开页面：`MaterialCommandRetentionDispatcher` 发现租户后通过非拥有者RLS和空业务权限上下文，只批量清除到期输入；未执行提交转过期，成功/拒绝等原结果保持。Worker支持单独选择 `WORKER_QUEUES=none` 与 `WORKER_SCHEDULERS=materialCommandRetentionScheduler`，关闭时等待当前批次，不能借清理执行耗用。普通业务消费者保持停止；物料清除已通过固定本地零消费者入口独立运行，实际周期和清理见[维护进度](../project-control/MATERIAL_RETENTION_PROGRESS_20261020.md)。它不自动注册开机服务或生产监管。

## 操作界面与来源分页

审核稿生产的原生产历史及已审核设计直接生产的已有安排，均接同一个物料面板。原BOM/单位/供料责任由服务读取。界面明确区分预留、实际耗用、释放、实际退料、工厂手工报告和原报告更正；输入数量及来源不会因刷新静默替换，依据变化须显式重新核对并再次确认实际情况。

`/stock-options` 与 `/reservation-options` 使用原绑定和行码，各页25条。库位游标采用物料/库位/批次的稳定维度，不用重建会变化的投影行ID。可选 `selected` 单独核对已选的后页来源，刷新时不退回第一页的其他库位；原选择失效则明确要求重选。`/entries/:entryId` 独立读取原记录的当前可释放/可更正余量和原库位，不依赖第一页历史是否仍包含该行。

浏览器不持久保存私有正文。先准备原提交再执行；写响应丢失只重新读取，页面刷新、新本人会话均读取服务端原提交及原事实。恢复执行须明确核对原填写，不能自动重发POST或生成新编号掩盖未知结果。读取失权清除私有表单与晚到响应；暂时读取失败保留填写并停用提交。
