# 制造BOM与工序版本

状态：1.1.34增量实施中，关联R12/B33及B34/B35/B37依赖。模板、整单制造选择、原提交恢复、运营V3交付/返工及工厂清单已有局部个人身份证据。0134/0135已登记且真实历史升级通过，普通库未执行。其他生产入口、完整回归、候选/恢复、普通采用、本人登录、实际耗用和产能预留继续，不计完整工作包完成；见[运营交接](production-operator-handoff.md)。各批历史证据分别保留。

## 业务与版本

制造模板固定一个明确SPU及产品规格身份，编号在SPU内不区分大小写唯一。每次保存创建不可变制造版本，同时固定所用规格版本、产出数量/单位、材料行、工序顺序和说明。不同裁切用途可以引用同一物料，行编号必须独立；材料可引用本版本工序，不能跨版本指向其他工序。

材料保存基本单位下的精确分子/分母、损耗数值与口径、供料责任。工序独立记录加工代码、责任、可选预计时长和说明。草稿允许未知，不自动填零、默认工厂供料或默认审核通过。审批要求材料及工序责任明确，物料启用且单位一致，耗量和损耗口径完整，当前产品规格事实完整。工厂地址、能力和实际工艺参数仍由原工厂版本拥有；不把产品材料模板当作工厂实际承诺。

新草稿与已批准的生产版本同时保留。当前草稿可被批准或驳回一次，改动结论需建立新版本。保存草稿不自动替换上一已批准版本；来源规格更改或产品归档后，原制造版本仍可在当前权限下读取，但不能继续形成新的备料建议。后续生产下达必须明确固定制造版本及独立工厂版本，不能自动回填到历史生产。

## 精确备料建议

一份BOM描述产出B个单位时净耗材料N/D个基本单位，拟产出Q个单位的净耗为`N×Q/(D×B)`。

- `add_to_net`表示在净耗上额外增加损耗量，毛需求为净耗乘`(10000+lossBps)/10000`。
- `fraction_of_input`表示损耗占投入量，毛需求为净耗乘`10000/(10000-lossBps)`，损耗必须低于100%。

所有计算使用整数与精确分数。保留各裁切行，同一物料、单位、供料责任下先汇总精确数值，再给出整基本单位上取整参考；不能累加每行上取整而重复备料。工厂供料和自有供料分开汇总。单位必须与物料主数据一致，不暗中把米、克、件互换；必要的换算须以明确基本单位数量重新填写。

该结果仅为提案，尚未扣减库存、预留原料、登记工厂耗用或产生采购/付款。实际领料、批次与退料继续归库存拥有者，后续接口需要独立执行证据。

现有库存账使用整数基本单位。接通实际消耗前，库存拥有者必须提供能表示分数耗量的计量精度或明确的最小单位/换算依据；不能把备料参考的上取整数量直接登记为实际耗用。该依赖继续归B40，不以本提案接口代替库存改造。

## 当前REST边界

| 方法 | 路径 | 当前权限与行为 |
| --- | --- | --- |
| GET | `/v1/manufacturing-recipes?spuId=...&after=...&limit=...` | 当前ProductRead及实际SPU范围，稳定编号分页 |
| GET | `/v1/manufacturing-recipes/references?spuId=...` | 当前SPU范围、实际规格事实就绪状态和维护限制 |
| GET | `/v1/manufacturing-recipes/material-options?spuId=...&search=...&selected=...&after=...&limit=...` | ProductRead及InventoryRead，活动物料分页与原已选物料分别回读；不可读取显式列出 |
| POST | `/v1/manufacturing-recipes` | ProductRead/ProductWrite及物料读取，创建模板和首版 |
| GET | `/v1/manufacturing-recipes/:id` | 当前ProductRead，读取当前草稿、最近批准版本及内容缺项 |
| GET | `/v1/manufacturing-recipes/:id/versions/:versionId` | 当前ProductRead，明确读取原版本历史 |
| GET | `/v1/manufacturing-recipes/:id/history?before=...&limit=...` | 当前ProductRead及原SPU范围，按版本号读取原历史分页 |
| POST | `/v1/manufacturing-recipes/:id/versions` | ProductWrite及物料读取，固定expectedVersion，新建版本 |
| POST | `/v1/manufacturing-recipes/:id/reviews` | ProductRead及独立`manufacturing:review`，批准时另核物料读取；实际说明与版本同笔固定 |
| POST | `/v1/manufacturing-recipes/:id/material-demands` | ProductRead及物料读取，只对当前已批准版本计算备料建议 |

新增`manufacturing:review`权限不会主动授予现有账户，角色配置和真实会话验收后续单列。所有写命令核对当前成员与对象范围；原请求的编号、内容、操作员及原响应一起固定，当前失权后不能恢复私有回执。原成功请求在产品归档后仍可在当前权限下恢复，且不新增版本或审核。

REST响应使用`{contextAuthority,data}`，权限标识来自本次实际事务的当前成员；原命令回执只固定业务data。新旧授权之间恢复原回执时不能复用旧contextAuthority。物料候选仅提供编码、名称、基本单位和启用状态，不含库存量、成本、库位及私有文件。

## 页面、登录与原请求

页面为`/manufacturing-recipes?spuId=<UUIDv7>&recipe=<UUIDv7>`；从具体规格新建使用`specificationId=<UUIDv7>&new=1`。SPU工具栏与规格行均有入口，作为商品规格的辅助页面，不增加独立主导航。个人登录保留具体模板或创建位置，来源返回链接可回到原规格。

表单保留未知数量/损耗与责任，精确数值接受十进制或分数；物料基本单位变化后保留旧数值，必须明确重新填写，不能静默换算。工序使用稳定行身份，排序或编号调整不会改变材料关联；被材料引用的工序须先解除关联再删除。长标题和版本名称可在390宽度换行，按钮有交互反馈，结构变化使用现有原生ViewTransition并尊重减少动态效果。

产品填写与原提交意图只在当前标签页暂存两小时，不含凭据或订单PII。提交前先固定原请求；响应丢失或不可校验时锁住本次内容，只恢复相同请求编号/正文。网关后验权限变化的409保留`authority_changed`，页面隐藏资料并保留原意图，不把它误作普通版本冲突。普通版本冲突需核对当前保存内容，再明确采用新版本依据；临时读取失败保留填写，当前读取范围真正丢失则清除私有内容和填写，迟到响应不能重现。

开发浏览器使用`pnpm test:e2e:order-daily --suite=manufacturing`；独立运行候选验收再加`--compiled-web --candidate=<ID>`。必须设置本批新`YUMMYAI_TEST_CACHE_DIR`，不触碰普通`.next`与历史被拒清理路径。测试采用实际OIDC、BFF、REST及数据库和合成账户，不能代替用户本人登录、普通部署或工厂验收。

## 数据层、Harness与Agent分工

0133新增制造模板、不可变制造版本、BOM行、工序、审核及命令回执表。每表强制RLS，产品规格、材料和工序使用租户组合外键。BOM行及工序必须在原版本创建事务内写完，旧版本不能迟到补行；版本序列在事务提交时检查。即使数据库拥有者也不能改写或删除历史版本、行、审核和回执。

服务使用现有商品拥有者范围和当前成员校验，按请求、商品父对象及模板取得一致顺序的锁。只锁可变规格身份，读取不可变规格版本时不申请UPDATE权限。版本、材料/工序、原回执和审计同笔提交，审计失败整笔回滚。Agent可辅助整理草稿和解释建议，不能代替供料责任确认、制造审批、实际消耗或工厂生产事实。本批不引入新Agent框架、队列、依赖版本或付费模型。

事务封存同时核对数据库事务编号与原事务时间；应用写入的创建来源由数据库填写，不接受调用方伪造。没有把当前事务编号写成不可移植的CHECK约束，避免备份恢复历史数据时重新要求旧行属于恢复事务。隔离测试覆盖相同事务编号但历史时间不同的旧版本，仍禁止追加组件；这项测试不代替完整候选的备份恢复演练。

开源依据先核对[ERPNext BOM](https://docs.frappe.io/erpnext/bill-of-materials)及其[开源实现](https://github.com/frappe/erpnext/blob/develop/erpnext/manufacturing/doctype/bom/bom.py)，借鉴材料/工序/实际库存的分工，复用YummyAI已有商品、库存和工厂模块。后续产能设计另参考[工序产能计划](https://docs.frappe.io/erpnext/production-and-material-planning-capacity-planning)，不将旧供应商容量快照当作工厂预留余额。

普通库本批未迁移，普通Worker未启动。验证只能使用一次性接纳运行器；历史0129普通环境与0130—0132局部候选的采用状态保持独立。原1.1.30 ZIP及历史拒绝路径均保留；制造基础首批5目标/20文件删除被自动审批以`blocked by policy`拒绝，累计583条路径只读冻结，未更换工具或路径重试。基础历史见[首批交付](../project-control/MANUFACTURING_FOUNDATION_DELIVERY_20261019.md)，本次页面、构建、验证及清理见[工作台交付](../project-control/MANUFACTURING_UI_DELIVERY_20261019.md)。

## 生产固定版本开发增量

下达整单、单件审核稿、直接生产和补做的新命令均须明确选择已批准制造版本，并由操作员确认订单数量采用销售SKU单位。API字段保留可选以解析历史原请求；新命令的服务门禁仍强制要求，不为缺项自动选择默认版本。相同操作员与原正文的成功回执在当前权限下恢复，不新增版本，也不要求旧请求补上新字段。

原审单生产从实际不可变制作修订解密、校验原始字节，再读取其中固定的销售配方、SKU、产品规格及工艺。直接生产必须有当前明确的产品声明、同一产品SKU的已审核原生设计及其有权使用的生产文件；已有审单时不能用新声明绕过它。沿用原文件的补做继承原生产绑定的商品、规格、工艺、尺寸口径及工厂能力依据；新审核稿补做重新核对新的原制作来源。旧单缺绑定保持未知，不能把今天的目录关联回填为历史事实。

工厂候选与实际提交共享这份原商品依据。今日渠道SKU关联变化不能改变原审单的工厂匹配条件；同口径尺寸须与实际审核稿一致，不同尺寸口径不做暗中换算。这里复用[ERPNext Work Order](https://docs.frappe.io/erpnext/work-order)的原BOM与制造依据分工，并继续使用本项目既有商品、工厂和生产服务。

`GET /v1/order-centers/lines/:id/manufacturing`在当前OrderRead、OrderPiiRead、ProductRead及原SPU范围内返回最小规格说明和已批准候选，每页25项。`originalProductionOrderId`仅接受同一商品的实际原生产，`after`为稳定版本游标；重复参数、调用方tenant与未知参数均拒绝。响应不包含材料库存、成本、BOM私有说明或订单解密正文。工厂候选端点另核对当前ProductRead及原制作来源。表单必须由人选择并确认单位；本轮实际浏览器验收仍待完成。

0134将制造绑定作为生产版本的不可变伴随证据，在同一事务固定原审核、原规格、原来源、数量单位、SKU、工厂依据及BOM内容校验。新应用生产版本没有绑定时，在提交前整笔回滚；迟到给旧版本补绑定也被拒绝。生产命令的版本、来源与审计保持同笔事务，既有租户RLS及当前成员范围继续执行。

真实历史升级使用`pnpm test:e2e:order-daily --suite=manufacturing-upgrade-integration --cache=false`。运行器先应用真实pre-0134迁移，使用普通应用角色保存历史生产、质检和V1交付，再执行当前迁移；核对原记录和V1清单checksum不变、旧绑定仍缺失、新版本缺绑定回滚、未知工厂继续阻止交付。历史交付文件在该用例中仅为不可恢复的合成元数据，不代表文件质量、工厂接受或备份恢复验证。完整集成命令已纳入此独立升级套件。

新V3交付已接通原制造内容快照、工厂最小材料/工序/责任、精确计划用量及明确生产说明；接受须携带看到的制造清单校验值，V1/V2不补造。工厂个人身份桌面/手机已局部验证，运营生产选择及交付页面仍需浏览器验证。实际领料、工厂耗用、采购、产能预留及正式生产仍是后续工作，见[制造交付契约](manufacturing-delivery.md)。完整平台保持48需求、54工作包和8阶段，最新恢复位置见[项目进度](../../PROJECT_STATUS.md)。
