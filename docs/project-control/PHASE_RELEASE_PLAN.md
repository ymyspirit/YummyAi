# 分阶段上线与收口约定

2026-10-24 · 用户授权：先上线已经完成的重构，每阶段同步GitHub并上线后继续下一阶段

## 执行顺序

阶段是业务里程碑，每个阶段拆成多个可独立验证的小交付。同一时刻只保留一个待上线交付；每个可审查的小改动及时提交GitHub并运行相关检查，不等整个阶段结束才集成。失败先修复当前交付，不继续叠加新的发布范围。

每个交付按固定顺序完成：确定一个用户可验证的结果和已知缺口 → 实现与相关快速检查 → 小提交和GitHub同步 → 对应提交的发布检查 → 形成固定构建 → 备份和部署 → 实际日用页面及运行健康核对 → 清理验收输出并写收口记录。发布候选完成项目规定的完整检查，同一候选已通过的结果可复用；只有源码变化、失败或未消除的疑问才扩大或重复检查。

部署与功能开放分别记录。付费或外部写操作可先以关闭状态部署，启用仍按用户原授权和业务门执行。数据库变更须保持新旧应用兼容并提供恢复方案；代码回退不自动覆盖上线后的真实业务数据。每次收口写明实际运行commit、构建、入口、可用行为、检查、回退版本、剩余缺口和下一交付。当前交付稳定后继续下一交付，整个阶段范围完成后再关闭里程碑。

本约定采用[DORA小批次交付](https://dora.dev/capabilities/working-in-small-batches/)、[持续集成](https://dora.dev/capabilities/continuous-integration/)及[Google SRE发布验证与回退](https://sre.google/workbook/canarying-releases/)原则；具体检查与本机切换仍遵守本仓库发布规则。

GitHub同步以可审查分支及PR记录，合并必须满足该阶段检查；部署记录绑定实际commit、构建及运行版本。未经检查的源码、只有测试通过的开发目录、未完成候选，均不能标成已上线。除非明确发布全平台候选，阶段上线不自动改变54个完整工作包或业务验收状态。

## P1 当前范围

基线为已采用的schema188、4052文件、source630fdef0、Studio2.7。新交付checkout只从该白名单复制源码，再加入配置读取修复与必要发布检查。根开发树189/190、尚未收口的付费生图、并行文本计费均保留，不混入P1。

发布仓库为既有公开仓库ymyspirit/YummyAi。提交前检查真实密钥、登录凭据、客户/订单资料、生产导出和本机运行记录；这些不推送。原工作区的未提交修改、用户资料、业务备份及既有健康服务保持；部署窗口才按当前真实进程身份受控切换。

## 每阶段的收口记录

每次发布只保留一份最新阶段记录，明确：范围与明确未完成项、用户可操作入口、基线/提交/构建/部署身份、相关检查及CI链接、备份恢复与失败回退、资料保全、测试资源清理、用户反馈以及下一阶段。旧证据可引用，不能被改写成新候选已重跑。

阶段状态以对应提交的GitHub检查、部署记录和当前交付状态为准。P1收口后才能进入P2；原有实现和局部验收继续作为输入，不因源码存在就自动计为上线。
