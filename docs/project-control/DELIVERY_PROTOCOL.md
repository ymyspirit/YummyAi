# YummyAI 项目交付、验收与返修约定

建立日期：2026-10-15，Asia/Shanghai。适用于当前 ERP 蓝图与后续获授权的软件实施。此文档不自行授权真实发布、付款、消息发送或生产。

## 1. 当前事实与范围

PRD、架构、设计样稿、8 阶段和 54 工作包已经形成，规划 v1.0 ZIP 保留。主蓝图当前为 1.1，已合并 PDF 辩证阅读/逆向方法、Harness、知识治理和创意保留专项；1.1 ZIP 是较早冻结快照。最新实施与验证以项目状态及其交付证据为准。

本机制建立时，软件工作包全部从“待现状核验”开始；现已按实际工作更新进行中及局部证据。这不等于现有 YummyAI 没有实现功能，也不代表完整平台已经验收。既有代码只在真实路径验收后计入对应交付。

范围由原 48 项需求和 54 工作包保持稳定，新增或删除范围时记录来源及影响。已有 P0/P1 产品边界继续有效，不能把 8 个建设阶段误作新的发布权限。

## 2. 怎样完整推进

S0 核对现状、补齐 Harness 执行规格及最新 PDF 推导的追踪关系，确认首发产品与必要接口；S1 建立可靠数据、权限、文件和任务基础；S2 完成商品到上架包；S3 准确接单与审单；S4 完成受控 AI、制作检查和审核；S5 贯通工厂接单、质检与返工；S6 贯通物流、售后与真实成本；S7 完成经营分析、第二品类、恢复演练、试点与交接。

按可演示的业务切片推进，相关契约、服务、页面、权限、异常、测试及文档一起交付。优先复用既有开源和内部模块。多 Agent 和新运行框架只有在具体需求与评测支持时引入。

首批实施先做现状核验，再从有基础的一类产品推进订单输入、Harness、制作审核及工厂接受的完整闭环。工期和复用率在有真实基线与首批交付后校准，不沿用假设工期作为承诺。

前轮 Harness 讨论中提出的方向需要延续到专项规格：统一任务与检查点、按业务对象组装上下文、版本化 Skill、受控工具网关、执行与恢复、任务/团队记忆分离、模型路由与费用、产物审核及可观察性。优先复用现有原生工作流、PostgreSQL、BullMQ、规则和 AI 服务；默认单流程及必要的单 Agent 步骤，多 Agent 经评测再决定。此处保存讨论方案，不表示这些能力已实现或已完成业务验收。

## 3. 怎样查看进度

唯一任务状态源为 state.json；仓库根目录 PROJECT_STATUS.md 和 PROJECT_HANDOFF.md 由生成器导出。每项任务保留 Bxx、Rxx、阶段、前置项、技术状态、业务验收状态、证据和下一步。

技术状态：待现状核验、待做、进行中、阻塞、技术验证中、技术验证通过。

业务状态：未提交业务验收、待用户验收、需要修改、已验收。

不以文件数量、代码行数、聊天轮次或模型自己的判断作为完成率。现状核验前不报软件完成百分比。技术验证通过需要实际证据和被验证的工作树身份；已验收还需要用户业务反馈记录。

开始一批工作时说明目标和验收行为，工作中报告关键进展与阻塞，每个可验证工作包结束时说明：改了什么、在哪里看、怎么试、测试覆盖及限制、剩余项。你可以随时说“当前进度”。

## 4. 每项工作如何算完成

- 对应需求和场景已明确，正常、空、缺项、失败、过期与权限状态可解释。
- 相关检查实际通过；涉及界面时通过真实浏览器走查，不能只提供配置或测试文件。
- 记录命令、关键结论、应用/工作树身份、产物校验值、外部回执与仍待验证项；截图与原始日志完成检查后按下述约定清理。
- 测试资源使用隔离数据并清理；必须保留的历史与未完成清理如实记录。
- 按用户 2026-10-16 的补充要求，Agent 在验收后删除自己生成的本地临时文件、原始日志、截图、trace、测试下载和可识别的测试缓存，并清理对应测试数据/资源。保留源码（含可复跑的测试）、PRD、进度/交付结论及必要的校验与清理记录。删除前核对绝对路径、归属和活动进程，不能删除真实业务文件、原始用户资料或跟随 junction 删除共享依赖。中断时先续做清理；遇到实际拒绝或占用需如实记录。
- 用户能按具体操作验收。反馈需要修改时重新打开任务。
- 正式发布独立核对候选提交、干净发布工作树、CI、配置/迁移、扩展包、备份恢复及对应业务验证；不得把开发验收当已发布。

平常业务操作是否需要人工审核，继续依据已确认的业务策略。对话中已经授权的操作不重复询问；超出授权范围或需要新的业务决定时才确认。

## 5. 中断与续做

任务边界、重要测试后和结束一轮前保存：当前任务、修改范围、验证结果、未完成命令、相关进程和端口的观察、业务测试资源、外部意图、阻塞与明确下一步。状态更新带 revision，派生文件可重新生成。

中断可能发生在保存前。恢复时必须比较真实文件、Git 和进程状态，而不盲信旧摘要。用户可在原对话或新对话发送根目录续做说明中的消息。

文件元数据检查点不替代代码或业务备份。可独立提交的改动只包含本任务范围；不自动暂存用户原有修改，不 reset/clean 无关工作。正式恢复仍须保留最新业务记录和外部动作，不能靠重放任务或回滚旧库撤销现实交易。

模型在对话断开后不保证继续运行；未设置自动调度。恢复后从已验证检查点继续。

## 6. 不满意怎样改

用户可以在任何阶段直接描述不满意的地方，不要求编写技术规格。推荐表达：

位置或任务：例如订单审单页 / B25
现在的问题：例如缺图原因不明显
希望的行为：例如直接显示缺哪张图并能返回修正
例子或参考：可选

每条反馈记录为 CHG-编号，关联原任务、用户原话/来源、期望行为、验收条件、涉及模块和当前状态。

功能偏离已确认需求：按缺陷处理，修复并回归原流程。
体验调整：将反馈转成具体页面与操作效果，交付可见结果供用户复看。
新增需求：记录新增范围、依赖和成本影响，先推进不受影响的工作，必要业务取舍由用户决定。

修改后展示实际变化和验证结果，等待用户确认该反馈是否解决。用户尚未验收时保持待验收；可以继续已授权的独立工作，不要求用户逐个内部步骤审批。

## 7. 用户与 agent 各自负责什么

Agent 负责内部拆解、选型核验、实现、测试修复、文档、进度与续做记录，主动推进已有授权范围。

用户负责真实业务目标、样品及制造要求、外部账户与工厂等必要条件、重要取舍和最终使用体验。只集中询问会实质影响结果的问题，常规实现选择由 agent 处理。

对发布、费用或正式生产等动作，按照已有明确授权执行；超出授权范围时说明具体动作、原因与待批准结果。

## 8. 状态维护命令

在 D:\YummyAI 运行：

~~~powershell
node docs/project-control/scripts/render-status.mjs
node docs/project-control/scripts/render-status.mjs --check
~~~

第一条按状态源生成两个根目录入口，第二条检查编号映射、已完成证据、业务验收记录和生成结果一致性。这些是项目记录检查，不是 ERP 功能验收。
