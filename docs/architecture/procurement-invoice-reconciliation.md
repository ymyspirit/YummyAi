# 采购发票差异、供应商凭证与后续收货核对

本规格属于 R27 / B39 / T13。它补充采购发票拥有者及本人持久命令，不代表 B45 / T17 的付款、汇兑或总账结算完成。

## 参考与边界

先核对开源 ERPNext 的[采购贷项](https://docs.frappe.io/erpnext/debit-note)和[采购退回](https://docs.frappe.io/erpnext/purchase-return)。采用其关联原票、另立纠正凭证及区分财务与实物影响的原则；本项目不复制其库存或会计过账逻辑。供应商术语可能不同，界面固定说明：贷项减少原票金额或数量，补差只增加金额。

这里的凭证号、日期和证据引用由有权限的操作者登记。引用字符串不是已验真的外部文件；本地审批不是供应商确认、实际付款、退款、税务核准或生产放行。实物退回仍使用实际来料/库存拥有者，财务数量冲销不会增减库存。

## 三种实际动作

`invoice_reconcile` 是第九种本人持久命令，目标始终为原发票 ID。原八种命令及其规范正文和校验算法保持不变。

1. `adjustment_record`：持有当前采购写权限的人登记供应商贷项或金额补差；生成不可变、待审核的实际凭证。待审核凭证不改变金额或收货占用。
2. `adjustment_review`：有当前采购审批权限的人，在自己的命令中引用待审核凭证 ID，核准或拒绝并给出原因。允许同人审批，遵循既有采购审批权限；不擅自增加强制双人制度。拒绝保留历史且不产生数量或金额效果。
3. `receipt_match`：有当前采购审批权限的人，把后来真实接受的收货行关联到原票未覆盖数量。它追加匹配，不把新事实伪装成原发票创建时的分配。

本人命令的 prepared 原文只对本人开放。同事从独立受权的实际发票详情和待审核凭证分页入口审批，不能访问或接管录入人的私有 prepared。执行核准是业务审批；执行后确认已读只清除私有正文，不是再次审批。

## 不可变事实和净占用

原发票、0149 原提交凭据、原分配、原采购版本、实际接受/拒收和库存流水保持不变。0151 追加 `inventory_invoice_reconciliations` 及 `inventory_invoice_allocation_effects`；处理事件本身是实际结果凭据，命令用独立外键引用它。

每张发票保存顺序、前一事件、原 0149 凭据、原 PO 版本、真实操作者、规范请求、校验和及实际插入事务。供应商凭证按租户、供应商、凭证类型和规范化凭证号唯一，不能换日期、扫描件或原发票重复使用同一凭证。本版一张供应商凭证关联一张原票；跨票贷项必须另有共享单据额度设计。

收货净占用 = 原 0149 分配 + 后续 consume − 经批准的 release。

- 数量贷项先抵减原票未分配的开票数量。只有超出未分配部分的贷项数量，才释放原票实际占用；release 精确引用原 allocation 或后续 consume，累计不能超过该来源。
- 纯金额贷项和金额补差均不改变收货数量。补开尚未开票数量继续走原 `invoice_record`，不得假装金额补差再次消耗收货。
- 信用数量累计不超过原开票数量；贷项金额不超过原金额加已核准补差减既有贷项。不静默截断，不四舍五入到最小货币单位。
- 后到货匹配必须同租户、原 PO 版本、行与单位；匹配量同时受真实收货净余量和原票净未分配量限制。原发票、其他发票和后续匹配共同争用同一净容量。

## 当前余额与历史结果

原始匹配状态照常显示。当前余额由实际事实重新计算，逐行展示原数量、已核准冲销数量、净数量、净分配、未分配数量、原金额、贷项、补差及当前差额。成功命令保存的 balance 是执行时结果；当前详情另行重读，不能用旧命令结果冒充当前余额。

`matched` 需要数量完整且同币种金额差额确知为零。金额为零但数量仍未覆盖时继续待核对。`fully_credited` 需要所有净数量及净金额均为零，并与正常匹配分开表达。EUR 原票对 USD 采购版本不推测汇率；部分冲销后仍保留异币未知。完整同币贷项可显示整票冲销，再由真实新票使用释放的容量。

无原 0149 凭据、历史分配未知或原单位/价基缺失的旧票如实显示未知，缺失单位和逐行金额保持 null，自动处理被阻止。不补造历史 proof 或以当前采购版本重建旧依据。显式人工历史基准重建及其审批尚属后续工作。

## 并发、权限与恢复

每次准备与执行重新计算业务指纹，包含固定原 PO 版本、相关发票与 proof、真实收货、原分配、后续效果、已登记处理链和历史未知状态。别的发票占用收货、另一审批或新收货都会使旧提案失效；恢复后须按新的实际依据重新填写，不能自动套用旧指纹。

锁顺序维持原操作键 → 本人命令行 → PO → 排序的收货行。所有访问使用 `withTenant()`、非拥有者角色和强制 RLS；执行权限是准备时上限与当前成员权限的交集，并核对实际对象拥有者。SQL 同时限制净容量、原分配来源、金额/数量上限、事件链及完整事务，不能凭成功状态制造事实。

事件、批准效果、审计与命令结果同事务提交。准备或执行回执未知时冻结原键和正文，重新读取原命令；新的本人会话从服务器恢复。七天留存、取消、到期和确认使用现有维护；清除私有原文不删除永久键、实际凭证和必要历史。

## 接口与验收

- `GET /v1/procurement/invoice-reconciliations`：最多 50 条、原页游标，可按 PO 和实际待审核凭证筛选；越过当前无权读取的对象，不能靠工作区前 100 条推断完整性。
- `GET /v1/procurement/invoice-reconciliations/:invoiceId`：精确受权详情、当前余额、可用收货、实际凭证、审批历史与指纹。
- 所有写操作通过既有 `POST /v1/procurement/commands` 及 execute/cancel/acknowledge；没有绕开持久命令的页面写接口。
- Web 对应只读 BFF `/api/procurement-invoice-reconciliations`；权限变化清理私有页面状态，迟到响应不能覆盖新身份。

验收需覆盖分次价差、数量释放、未分配超开量、金额补差、后到货匹配、容量竞争、重复纸据、异币/历史未知、撤权、审计回滚、SQL 绕过、跨会话恢复、真实 API 提交前后中断和真实 150 → 151 升级；桌面与手机实际页面需核对原始状态及当前余额。所有新数据、构建、日志和测试资源均为可删除隔离资源。当前完成证据另记进度，不以本规格或测试设计冒充通过。
