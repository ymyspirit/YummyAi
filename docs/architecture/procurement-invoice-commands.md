# 发票原提交与跨会话恢复

本切片将实际供应商发票登记接入既有采购命令，追加第八种 `invoice_record`。0150 只在一次性隔离资源中验证，普通数据库及服务仍为 148。本地 Responses 渠道已接入，凭据与默认值保持。实际验收与剩余范围见[本轮进度](../project-control/INVOICE_COMMAND_PROGRESS_20261020.md)。

## 数据层

发票事实仍由 0149 的 `inventory_supplier_invoices`、明细、原请求凭据及收货分配保存，不另建发票副本。命令新增 `invoiceResultProofId` 外键指向 149 原请求；旧 `resultProofId` 继续只指向 146 采购凭据，两域由 SQL 互斥约束。发票没有自身版本，公开结果中的版本字段为 `null`；采购版本只作为原依据。

新增命令必须指定原 PO 版本。原 149 raw 接口继续允许旧输入省略 expectedVersion，历史原请求摘要逐字保持：`{version:1,purchaseOrderId,input}`，保留行顺序，仅按原规则规范日期。旧七类命令和旧六种 raw 写入种类不扩为发票，不改变旧规范字节、密文或账本。

## Harness 层

准备只保存本人加密原填写和权限快照，不创建发票、收货分配或成功凭据。预览读取指定历史版本，以本张票的数量、单位、币种、价格及计价数量显示真实金额；不从最新列表补造原依据。原请求保存七天，确认、取消或到期按现有机制清除密文，实际发票事实和不可变原凭据保留。

执行在同一租户事务中调用实际发票 owner，写入发票、明细、真实 149 凭据、分配、审计和命令成功结果。成功需要原始完整事务 ID 对应的新发票与该事务的新凭据；反向延迟约束禁止真实发票已提交但命令未绑定结果。已有 raw 发票不可事后追认为今天准备的原命令。

锁顺序为原操作键、命令行、发票幂等键、PO、按 ID 排序的收货行。raw API 和 SQL 头记录使用同一前置准入。确认或密文清除不释放操作键，不能改走 raw 接口绕过命令。

当前成员身份与权限重新加载并和准备时权限取交集。原输入只对原操作者且当前可读的对象恢复。成功结果通过真实 149 proof 定位，不依赖私有输入或当前列表前 100 条，因此确认清除后仍可按权限读取。

## Agent 与界面

发票表单通过现有个人命令 BFF 准备、核对、执行、恢复及确认。响应不确定时读取同一原提交，不能新建提交键。关闭窗口不取消准备；新本人会话可以从原命令继续。界面将金额 matched、数量 allocation 以及未知差额分开呈现。

采用现有开源 Zod、PostgreSQL、Drizzle、Lucide 和 ERP 组件，不增加依赖。流程参考开源 ERPNext 的[采购发票](https://docs.frappe.io/erpnext/purchase-invoice)对象关系，保留本项目整数 minor、九位数量、租户与不可变历史约束。

完整财务对账、贷项/差额核销、真实供应商试点、普通 150 采用及用户本人页面验收继续单独完成。
