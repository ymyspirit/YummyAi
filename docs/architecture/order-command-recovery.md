# 生产命令持久恢复设计

2026-10-20 · R20/R22/R39/R43，B09/B26/B28/B51。首批直接生产、审核稿单商品和整单已实现服务端意图、尝试、最小回执及事务内凭据，并完成本地集成、真实重启和浏览器刷新/新会话验证。0136已受控进入普通环境；契约和剩余边界见[生产恢复](../integration/production-command-recovery.md)。

## 现有基础与目标

复用现有 PostgreSQL、订单权限拥有者、生产命令幂等回执、订单私有资料加密域和个人 OIDC。首批接通直接生产、审核稿单商品下达和整单下达；交付包、工厂回执及返工沿相同契约逐个接通后分别验收。完整平台其他执行域继续沿自己的拥有者，不建立任意 REST 重放网关或平行业务账。

数据层保存租户隔离、原操作员拥有的不可变命令意图和执行尝试。Harness 固定并核对原输入、权限上限、资源、版本及执行凭据，协调结果查询和明确恢复。Agent 可以解释状态与建议操作；制造确认、工厂接受和正式生产继续由对应业务角色操作。

## 请求与权限

在调用业务写入前，服务端固定白名单操作、合同版本、原路径、经现有Schema解析的原正文、业务幂等编号、原申请人、原权限/范围上限、订单/商品及来源版本。正文使用现有订单私有加密域，避免在日志、URL或浏览器持久缓存中留下私有说明。记录及每次恢复仍经过非拥有者`withTenant()`、当前有效成员和对象拥有者授权。

准备成功后执行原请求；准备响应丢失时按原业务编号恢复准备结果，或在当前订单中查询本人未确认的意图。不同操作员、不同租户或不同正文不能复用同一意图。失权、来源到期或匿名化后停止解密和展示；临时读取失败保留原意图状态，不能改用新编号。无私有资料、从未进入审单的原生订单仍遵循现有来源规则，不为恢复补造审单或顾客资料。

## 事务与执行凭据

准备、认领执行、业务提交和结果封存是不同事实。认领可使用有限租约；恢复始终使用同一原输入和原业务幂等编号。未知结果由操作员明确恢复，不自动重新执行。

认领状态须在业务事务中再次检查。生产拥有者取得原命令/订单锁后，通过内部执行凭据检查回调，锁定并核对当前意图、操作员及租约token，再进行业务写入；该行锁持续到业务事务结束。新认领须等待旧事务释放此锁。旧执行在新认领之后到达时因token失效在写入前拒绝；旧事务先提交时，新执行通过原业务回执恢复同一结果。

实现时保持一致锁顺序：当前权限检查、既有业务锁、意图行锁；认领及结果封存的短事务不在持有意图行锁时再调用生产事务。行锁冲突与释放依据[PostgreSQL显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)，具体迟到执行与死锁边界仍须按下述真实事务用例验证。

对外只接受意图ID，租约及内部回调不进入用户可填请求。准备服务不能跨模块直接写生产表。生产拥有者需提供最小、可信的事务提交回执；现有“提交后再读取完整DTO”的错误不能被误判为未提交。网络/进程中断或提交结果不可确认时保留未知；仅有明确的拥有者事务失败证据才能判定未提交。

成功但响应丢失的意图保持可发现，直到本人确认已读；确认只改变恢复投影，不删除原意图或业务历史。已知成功后的刷新失败维持成功事实。旧执行的结果可保留为尝试证据，但不能覆盖新执行状态。准备态、未知态及同一业务范围的并发新命令须按明确规则阻止重复意图，不能让刷新或另一设备绕过旧请求。

## 必须落地的验证

- 真正刷新/新浏览器会话后找回同一原正文和编号；准备响应与业务响应分别丢失。
- 数据库/进程重启及两个设备并发恢复；强制暂停旧执行后换租约，证明迟到旧执行零写入。
- 业务已提交但读取/结果封存失败，恢复只返回原生产，不多建记录。
- 原输入/主体/路径篡改、跨租户/跨操作员、当前成员/权限/范围变更及旧成功响应隔离。
- 旧规格、已满数量、到期/匿名化、从未提供私有资料的原生订单，以及整单与单商品的冲突边界。
- 固定制造和规则版本，保留原确认，不由Agent重建请求或重新勾选确认。
- 仅一次性测试资源；检查有效输出目录，原始日志/截图/下载在验收后清理并独立复查。

## 独立到期清除的后续实施约束

2026-10-20只读核对：实际依赖为BullMQ 5.80.5，现有生产命令服务在访问时清除已到期或来源失效的正文，尚无不依赖访问的扫描。沿用现有数据库、`withTenant()`及Worker任务边界，不为这一缺口升级运行框架或另建订单事实。BullMQ的[任务自动删除](https://docs.bullmq.io/guide/queues/auto-removal-of-jobs)由新任务完成/失败时触发，不能用它证明私有数据库正文按时清除；[幂等任务原则](https://docs.bullmq.io/patterns/idempotent-jobs)用于重复投递和重启后的安全重试。

实施时，可信任务只传租户内的记录定位与最小任务身份，不传解密正文或调用生产执行接口。过期与来源可用性以数据库时钟和原固定期限为准，处理已经失权、无人再次打开的记录。清除加密正文和执行凭据，保留原意图校验值、真实业务回执和必要历史；不能把清除当成取消现实生产或证明原提交未发生。扫描、读时清除及认领失效应共用数据保留语义。

采用有限批次、原子更新和可续做记录，不用一次全表锁。并发扫描可按[PostgreSQL行锁](https://www.postgresql.org/docs/current/sql-select.html)对队列式工作跳过被锁行，但跳过不能被报告为完整清除；必须继续下一批或以后补扫。既有生产锁后持有意图共享锁直至提交的顺序保持，清除不得持有意图排他锁后再进入业务生产事务。普通Worker启用与已有积压独立管理，隔离验证不得启动普通队列。

必须用真实隔离数据库/Worker证明：完全不访问页面仍清除；未到期不清除；数据库与主机时钟有差异仍正确；来源更早到期或匿名化及时清除；失权后不再解密但保留规则继续；跨租户和伪造任务被拒；两个清除执行者及中途重启可续做；认领/生产提交/清除竞争保持原业务事实和迟到零写入；投递丢失能补扫，且重复任务不产生生产或外部调用。以上为下一步规格，尚未宣称实现或验收。
