## 1. 阅读结论

这份材料适合作为买建判断和组织分工框架。其价值集中在维护能力、完全成本、业务资料沉淀和责任归属。它没有提供统一模型实测、已跑通的全链路成本或适用于 Amazon Custom 的生产架构，不能据此直接定模型、定预算或宣称无人经营。

原文已经明确标注多项限制：阶段是演讲者观点，评分是主观初评，价格是快照，成本是预算演示，案例仍待样品与成本验证。因此批判性阅读应保留这些限制，不能把作者已说明的假设误说成作者声称的实绩。

## 2. 哪些值得采用，哪些需要改造

| 原文内容与页码 | 判断 | 适用条件与 ERP 落地 |
| --- | --- | --- |
| 团队人数只是协作成本的参考，维护能力和定制必要性更重要，P8—9 | 采用 | 每个业务模块先判断买、接或建，列负责人、接口、维护预算与退出方案 |
| 用同一任务比较工具并记录改稿、复核分钟，P7 | 采用 | 增加统一样本、验收规则、重复运行与完全成本记录，避免凭体验排名 |
| 订阅与 API 的完整费用应一起核算，P13—15 | 采用并补充 | 计入评测、数据、开发摊销、失败重试、人工、异常、停机和迁移；比较同等合格交付量 |
| 数据层、Harness 层、Agent 层，P17—19 | 作为职责图采用 | 在工程上继续明确业务事务、安全、权限和外部对账边界；三层图本身不是生产架构 |
| 知识库保存依据、Skill 保存方法、数据库保存事实，P19 | 重点采用 | 规则中心、方法版本、订单事实分别有所有者；检索或记忆不能覆盖订单原始事实 |
| 按选品、内容、广告、库存职责协作，P20 | 采用职责分工 | 原文也说明同一 Agent 可分步完成；先验证确定性流程加单 Agent，再判断是否需要多 Agent |
| 统一店铺、SKU、期间、币种和时区，P18 | 采用并扩展 | 加入订单商品号、渠道映射生效时间、工厂地点、生产配方和数据可比性标识 |
| 公司、业务负责人、Agent 的责任分开，P23—24 | 采用 | 公司负责授权、安全与供应链；人负责目标及验收；Agent 只能在授权范围执行 |
| 场景模型评分与模型搭配，P12、21 | 作为候选假设 | 作者已说明没有统一实测；不把分数当准确率或收益率，不固化到模型路由 |
| 全链路自主经营的阶段趋势，P5 | 保留为预测 | 当前 ERP 的验收继续围绕具体交付、审核、错误率和恢复能力 |

两个假设反例有助于应用这个框架：两人团队若有高频固定的定制处理需求和明确维护预算，局部自动化可能值得；几十人的团队若只是偶尔做分析且现成工具足够，也未必需要统一自建 Agent 平台。它们支持原文的双轴判断，不能用人数区间代替业务证据。

## 3. 成本：算式正确不等于可用于预算

### 原文算术核对

- P13：1,000 次任务，每次累计输入 10 万、输出 2 万 token，即输入 1 亿、输出 2,000 万。按原文 Flash 单价计算为 360 元；Pro 为 1,440 元，算术成立。
- P14：订阅方案为 1,800 + 4 × 200 = 2,600 元；自建示例为 360 + 300 + 12 × 200 = 3,060 元。它直接说明低模型费不等于低总成本。
- P21：1.44 + 0.18 + 2.80 + 0.96 + 0.68 + 2.52 + 0.08 = 8.66 元。主 Agent 的 0.08 元在该页没有 token 明细，只能作为给定假设计入。

这些数字是原文给定条件下的复算，不是 YummyAI 已发生费用。没有同批任务实跑，不能确认订阅额度是否足够，也不能确认 API 使用量、成功率和人工复核相同。

### 对 YummyAI 更有用的口径

单位合格交付完全成本 =（模型 + 工具与数据 + 基础设施 + 人工复核 + 错误返工 + 开发维护摊销 + 可归属风险损失）/ 验收通过的交付数量。

模型费还需记录模型版本、地区、服务层级、输入与输出量、缓存读写、图像规格、重试和价格有效时间。P12 的主观评分不能替代该口径。

仅作敏感性示例：若人工复核由 6 分钟增至 12 分钟，按假设 60 元/小时，每单多 6 元；即使模型从每单 1 元降到 0.1 元，完全成本仍增加 5.1 元。这里的时间与工价是解释算式的假设，不是团队现状。

### 官方资料抽查

2026-10-15 抽查的部分单价与原文一致：百炼 qwen3.8-max 的相应全球/北京口径为输入 12、输出 36 元/百万 token；MiniMax-M3 标准服务且输入不超过 512K 的口径为 2.10 / 8.40。百炼同时存在其他地域部署价格，MiniMax 也有长上下文及优先服务价格。因此不能把单行快照推广成任意部署的固定成本。

来源：[百炼模型价格](https://help.aliyun.com/zh/model-studio/model-pricing)、[MiniMax 定价](https://platform.minimax.cn/docs/pricing/overview)。[DeepSeek 官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)也列出峰谷和缓存差异；[Kimi 计费说明](https://platform.kimi.com/docs/pricing/chat)另列缓存写入规则。其他单价与订阅套餐未完成逐项核验，本文件不认证整张价格表为当前有效。

P12、P21 写“来源见备注”，但本次提供的 PDF 在相关页未发现链接或注释对象，无法从该副本追踪所有评分与报价来源。这是该交付版本的证据限制，不证明作者没有其他来源资料。

## 4. 三层图如何转成可运行系统

| 责任 | 保存什么 | 不承担什么 |
| --- | --- | --- |
| ERP 事实与事务 | 产品事实、订单、库存、金额、版本、状态 | 不让语言模型自行决定账本或权限 |
| 知识与方法 | 可引用资料、适用范围、Skill 输入输出和验收 | 文档或经验不自动成为可执行规则 |
| 运行与控制 | 任务快照、工具白名单、预算、租约、恢复、审计 | 不把对话历史当可靠任务状态 |
| Agent 推理与协作 | 分析、草稿、工具调用计划和候选产物 | 不自动获得采购、退款、生产或广告权限 |

这四项是职责细化，部署上仍沿用模块化单体和 Worker。无需因阅读三层图就引入新框架或把现有 ERP 全部重写。

“主 Agent”在本项目优先解释为任务协调入口。确定性工作流管理依赖、等待、重试和状态；模型在有价值的步骤负责推理。多 Agent 只在独立子任务、并发收益、上下文隔离或专门复核得到实验支持后采用；同时计入交接错误、额外 token 和观察成本。

## 5. 猫墙架案例不能直接复制到 Custom

P21 的 4 件套猫墙架是待验证的标准化备货案例，包含 120 套试单、入仓、可售库存和上线投放。这里可学习的是依赖顺序：产品事实先确认、物流核价前置、可售及审核通过后投放。

Amazon Custom 的核心则是买家下单后形成个性化制造输入。需要补上：

1. 买家文字、原图、字体颜色和选款与订单商品的精确对应。
2. 下单时有效的销售映射、生产配方、规则和供应能力。
3. 实际生产文件、技术检查、必要校样与版本审核。
4. 工厂接受、拆单数量、实际产能、质检和返工。
5. 截单时间、实际交运、地址隐私、退款和完整利润。

Amazon 官方要求 Custom 订单由卖家履约，不能照搬 FBA 成品备货链路。[官方依据](https://sell.amazon.com/programs/custom)

## 6. 下一步如何验证，而不是相信模型排名

设计三个小实验，使用获授权、脱敏或专门构造的数据。此处是实验方案，本轮尚未执行付费模型评测。

| 实验 | 样本与基线 | 检查 | 决策 |
| --- | --- | --- | --- |
| 订单审单 | 30—50 条代表性商品行；先有人工标注与规则脚本基线 | 缺项、歧义、文字/选项映射、拒绝越权、复核分钟、单位合格成本 | 只有减少总成本且没有关键安全错误时进入辅助试点 |
| 制作与核对 | 不同输入质量、文字长度与工艺的固定样本；对比模板流程 | 实际像素、内容准确、几何、一次通过率、费用和恢复 | 确定性步骤保持服务执行；模型只承担必要内容处理 |
| 广告诊断 | 同一版本报表、成本与归因窗口；最多比较 2—3 条候选模型路由 | 算术、证据引用、建议边界、未知项处理、改稿和成本 | 先输出建议，验证后再单独评估受控执行 |

样本量是试点建议，不意味着统计显著或生产可靠性证明。危险动作、跨租户读取、漏检关键生产约束等属于硬失败，不用其他高分抵消。

## 7. 对正在编写蓝图的具体影响

- S0 增加逐模块买建判断、可维护负责人和完全成本基线。
- R04 明确知识、方法和业务事实三种资产的版本及权威边界。
- R20 增加候选模型实测、路由版本和单位合格交付成本，不按本材料的主观分数选型。
- R39 以持久工作流管理状态；对话与 Agent 不能替代数据库事务及外部对账。
- 开发顺序先形成单条可验收流程，再扩大自动化与协作数量。
- 组织上保留业务结果负责人、技术维护负责人和审核责任；人员兼任时仍区分每次操作的角色。
